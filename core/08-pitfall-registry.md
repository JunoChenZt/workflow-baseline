# 08 已知坑表：格式 · 维护协议 · 扫描

> **何时读**：要给项目建坑表；撞了坑想知道是不是老坑；节点起步要扫坑表；retro 的 must_update 要落盘。
> **骨架不含任何一条具体的坑**。坑是项目资产，在 `{{pitfall_table}}`；本文件只定它长什么样、怎么维护、怎么扫。

## 1. 条目格式（强度 × status 双维度）

**强度**（影响范围）：

- 🔴 **Hard Block** — 触发即**不得合并**；必须修主路径 / 修 fallback
- 🟡 **Soft Flag** — 触发可继续，但必须记 `quality_flag` / 入 deferred / PR 描述说明
- 🟢 **Nice** — 不阻塞，记趋势

**status**（当前生效性）：`active`（默认）/ `mitigated`（已有守护兜底，不会再触发，但保留记录）/ `stale_candidate`（疑不再相关，待交接审视）/ `retired_after_phase_review`（交接后判定退役）。

**一条坑的写法**：

```
- 🔴 [active] <一句话说规则>（<立档日期> · <出处：retro / PR / 事故链接>）
  <暴露方式：靠什么才抓到的>；<守护：焊进了哪条测试或检查；没有守护就写「无守护，靠本条」>
```

必带出处；有守护的写守护在哪 —— **坑表条目的理想终点是被一条测试替代，然后标 mitigated**。

**分段**：按项目阶段 / 模块分段（通用一段 + 各阶段一段），扫描时只读相关段。

## 2. 维护协议（只增不减）

**原则**：一个周期内坑表默认只增不减。坑的价值不是「当前一定还会发生」，而是「防止本周期内重复踩」。

**允许**：新增（经 retro must_update）/ 补触发条件 / 补规避方法 / 改 status（active → mitigated）/ 标适用范围缩小 / 升强度（仅当连续多次 retro 命中或数据驱动）。

**禁止**：直接删除 / 把 🔴 降成不存在 / 删历史原因与证据 / 周期中途批量「清理」。

**退役**：只在里程碑交接（[07 §2](07-pr-and-handoff.md)）或周期结束统一审视；用 `retired_after_phase_review` 替代物理删除；删除须 PR 说明 + 替代证据 + 用户确认。

**为什么不删**：历史证据留给后续 retro 引用；防 agent 为了文档清爽删掉没充分验证的坑；交接时系统性回顾比中途零散删更稳。

**加流程之前先问**：这条教训能不能焊进测试或删掉产坑的机制？能就别加流程。坑表越长，扫描越贵、命中率越低。

## 3. 元规则（不属于任何项目、值得进骨架的几条）

这几条在原项目里反复出现、且对任何项目成立，作为坑表的「通用段」种子：

- **报「0 问题 / 全绿」前先证工具看得见全部对象**。枚举有盲区时产出的是盲区形状的假 0，表面无异常。报 0 时附成立条件（扫了多少、凭什么是全集）。
- **守卫要锚在它真正要守的对象上**。整句匹配 ≠ 锚定那个数字；兜底常量 ≠ 运行时实配；别名写法先归一。锚错对象两个方向同时坏、只测典型例子看不见。
- **放宽检查 = 造盲区**。放宽识别范围前必问「哪种形态会变得看不见」；自己给守卫写的测试最容易把 bug 钉成预期。
- **记录里的承重数字要取系统自己写的字段**，别用临时正则数凑数；分类计数之和对不上总数 = 手写数。
- **「样本量」不等于行数**。同一次上游取数的多行共享一个时间戳，按行数算会成倍高估支撑度。
- **「我没看到」≠「没发生」**。下「某事没发生」类论断前先查它锚在哪个一手事实。
- **先证设计再判 bug**。判「bug 还是设计」前先 review 设计文档 / 注释 / commit；一手材料缺失时显式标「以下为推断」，动手前确认。
- **读记录先认主干的 tracked 版本**。调查任务常在分叉分支上跑，工作树同名目录可能只剩残留；`git ls-tree <main> <dir>` 先拉正式清单。
- **复用先例要抄整套守卫，不只抄正则**。
- **变异前先 commit 当还原锚**；**同工作树多 session 破坏性操作前当场重查**。

## 4. 扫描（节点起步，M 档建议 / L 档必派）

**subagent 化**：坑表全表长（数百行），主对话直接读会吃掉大量 context。派一个无状态 subagent 读全表，返回 ≤ 5 条相关坑的结构化 alerts（< 30 行）。

**输入**：任务描述 / 阶段 / 涉及的文件与模块 / `<goal>` XML（若已拆）。

**输出**：

```xml
<pitfall_alerts task_ref="…" phase="…">
  <scanned_sections><section>…</section></scanned_sections>
  <alerts count="≤5">
    <pitfall ref="§x.y" severity="🔴|🟡|🟢" status="active|mitigated">
      <pitfall_text/><relevance>本任务改 X，触发 Y 约束</relevance><action>改动前先 …</action>
    </pitfall>
  </alerts>
  <skipped_irrelevant><section ref="…">原因</section></skipped_irrelevant>
</pitfall_alerts>
```

**约束**：subagent 不修改坑表（落盘是 retro 的职责）；alerts > 5 = 任务范围过大，先拆再扫；对应阶段段落为空 → 输出空 alerts 并标注「该阶段坑表未建立」。

**下游**：每条 alert 的 `<action>` 必须落到 `<goal><stop_conditions>`（[02 §4](02-decompose.md)），不能丢。
