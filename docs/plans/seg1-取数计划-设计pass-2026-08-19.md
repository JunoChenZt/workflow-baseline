## 1. 大白话导读

### 1.1 现在是怎么运作的

用户提一个问题，系统在正式分析之前先跑一段"资料准备"——**这一段几乎不动脑子**：

1. 先判断这个问题是"问某只股票"还是"问一个主题"（这一步用了模型，是整段唯一动脑的地方）
2. 然后**按这个标签开关数据源**：问股票就去拉行情和新闻，问主题就去拉宏观和新闻
3. 宏观那一路，拿用户的问题去撞**一张写死了 13 个词的表**——撞上哪个词就拉哪个指标，一个都撞不上就**默认拉美国 CPI**
4. 拿回来的东西编上号，放进一个"资料夹"，后面八位分析师、辩论、基金经理读的都是这一份

### 1.2 出了什么问题

这套做法有一个共同的毛病：**它没有"我不知道"这个状态**。

- 问"黄金会怎么走"，表里没有黄金这个词，于是**默默拉回了美国 CPI**，当成证据写进资料清单。数据是合法的、有时间戳、格式完好、日志里一个字都没有——**它连自己问错了都不知道**。
- 问"某公司的毛利率"，因为"毛**利率**"里含着"利率"两个字，于是去拉了**联邦基金利率**。
- 问黄金的时候，因为被贴上"主题"这个标签，**行情那一路整个被关掉**——而黄金明明是有真实价格可查的。上一次正式跑批里，唯一被下游改写过的数字，正是那个只能靠模型上网捡回来的买入价位。

### 1.3 一个刚查到的、更要紧的事

系统里**已经有六个可以被分析师自己调用的取数工具**，八位分析师加基金经理现在就在用。

但那个查宏观的工具，**说明书上只写了四样**（通胀、失业率、GDP、联邦基金利率），认不出就给 CPI——它背后走的**就是我们要拆掉的那张表**。而拿新闻的那个工具，**参数是空的，问题压根传不进去**。

**所以这个毛病不只在资料准备这一段，分析师那一层也一样。** 今天分析师自己去问黄金，拿回来的同样是 CPI。

⇒ **只换"谁来决定查什么"是不够的，工具本身也得变强。而工具是两层共用的，改一次两边都好。**

### 1.4 改成什么

把那张表拆掉，换成这样一条链：

> **读懂问题 → 出一份取数计划（要查哪几样、每样具体查什么、为什么查）→ 代码逐条校验 → ★ 交给用户过目确认 ★ → 代码去执行、编号、放进资料夹**

关键在于**不是放它自由地乱调工具**，而是**它只负责出计划，干活的仍然是代码**。这样三件事同时成立：计划里编造出来的东西过不了校验；执行过程仍然是确定的；成本只多一次思考。

**规划员上岗前得先读过说明书**（2026-08-20 补）：出计划的前提是知道每个数据源的脾气——哪个库只认英文、哪个库搜了词会拿不相关的凑数、哪个数字要看同比才有意义。这些脾气没有一条是常识，全是我们逐个实测出来的，所以要把五份"数据源使用说明"的要点连同正反例一起写进它的工作手册；**而且说明书将来更新了，手册必须跟着更新**——这一条有机器盯着，不靠人记。

### 1.4b 为什么要加"用户确认"这一步（用户裁决 · 2026-08-19）

**一句话理由：在这里花一分钟，能省掉后面几乎全部的钱。**

实测（[2026-08-14 两跑归档](../observations/bc-final-e2e-20260814/FINDINGS.md)）：一次完整跑批 = **294 次模型调用 / $3.27**（两跑合计），**平均一跑约 147 次**。而资料准备这一段**只占其中 1 次**。

⇒ **在资料准备段结束时设一道确认，把关的是后面约 146 次调用、接近全部成本。** 拿错了资料就往下跑，等于拿这笔钱去分析一份错的材料。

**四条配套规则（用户定）**：

1. **确认放在校验之后** —— 用户看到的是"已经核过、代码都真实存在"的计划，不是可能含编造项的草稿
2. **每次都要确认**（不做"只对存疑项确认"的简化）
3. **不满意可以打回重找**，也**可以自己改**，**一直循环到用户点头为止**
4. **支持自动确认** —— 给无人值守的跑批用

**一个顺带的好处**：被用户确认过的那份计划，天然就是一份"锁定的、可回放的"计划 ⇒ **它直接解决了下一节要说的"重跑不一样"问题的一大半**。

而且计划里天然带着"为什么查这一条"——这正好是另一笔账要的东西（现在资料清单里，答非所问的、当背景的、真对题的，长得一模一样）。

### 1.4c 还差一道「收货验收」（2026-08-20 · 五个数据源逐个摸清之后补上的）

把五个数据源逐个真调实测之后，发现光有"下单前把关"不够——**有四个源会规规矩矩地交来不是你要的货，而且单据齐全、不报任何错**（⚠️ 这四个就是后面收货验收要逐条核的那四个，别记成三个）：

- 研报平台：你搜"黄金"，它把相关的排前面，但**够不上一页就拿铜、锂、澳洲贸易来凑数**——实测有一次 20 条里只有 4 条真讲黄金
- 宏观库：搜不到的时候**不吭声**，返回一个"一切正常、命中零条"
- 新闻源：那些过滤开关今天管用，但它**没有任何书面承诺**，哪天失效不会通知我们
- 行情源：要比特币的价格，**拿回来的是另一个东西的价格**——数字合法、时间戳齐全，差了两千多倍

所以在"代码执行"和"编号装袋"之间要加一步：**照着计划单收货验收**——搜黄金拿回来的凑数条目、要这只股票却拿回另一只的价格，都在这一步被挑出来，降级或者退掉，并记一笔。

这一步还救了另一件事：计划里每条写着"这是针对本问题的"。如果不验收就装袋，一次搜索带回的 16 条凑数货会**集体盖上"对题"的章**——比今天不打标签还糟。所以标签必须打在**验收通过的货**上，不是打在订单上。

### 1.5 为什么值得现在做

这一次改动能一口气解决**六笔已经立账的问题**（关键词表缺资产类、撞子串认错、主题类问题拿不到行情、资料清单分不出对题还是背景、新闻源根本不带问题去问、以及**研报只看标题不看内容**）。原本这些是分散的六条，各改各的会把同一处代码翻来覆去改六遍。

> ⭐ 第六条是 v3 才并进来的：原本以为"要看研报内容"得等平台开放原文，摸清之后发现**原文根本不存在**，但平台自己写的摘要拿得到、还带出处——所以它不再是"另一个项目"，就在这次里一起做（账目见 §6）。

### 1.6 代价是什么

**最主要的代价是"重跑不一定一样"。**

现在这一段基本是纯规则，同一个问题永远拉同样的东西——你们验证"我改了一处、下游有没有变"就是靠这个。换成会思考的环节之后，两次跑可能拿到不同的资料，就没法逐条对照了。

**解法**：把那份取数计划**存进归档，并且做成可以回放**。验下游改动时就用归档里那份原计划重跑，这时下游是完全确定的（比今天还稳，因为今天连第一步的判断都可能飘）；验取数本身时才让它重新想。**不确定性从"到处渗"变成"一个想关就能关的开关"。**

⭐ **加了用户确认之后，这件事变简单了**：被人点头的那份计划**本来就得存下来**（否则"确认过"这句话没有凭据）。所以"存计划"不再是为可复现额外付的成本，而是确认机制自带的产物。**两件事合成了一件。**

### 3.1 现状分解：哪些换、哪些留、哪些改造

资料准备段（图上的 `build_context` 节点 / 分段跑批的 ① 段）今天做八件事。按本方案的处置：

**结论：不是重构整段，是换掉「大脑」、保留「手脚」。**

**接缝已经存在**：今天「这次激活了哪些源、每个源为什么被激活」本来就是一个会落进资料夹、供追踪渲染的结构（[builder.py `source_routing`](../../src/committee/common_context/builder.py)）。**取数计划是它的超集**——从「激活了谁」扩成「激活了谁 + 各查什么 + 为什么」。不是插进一个没有位置的东西。

**真正往下捅的地方**：今天每个数据源**自己决定查什么参数**。改造后参数由计划传入。⚠️ **这条路已经走过一半**——查股价那两个源早就改成从外面收代码、注释明写"不靠猜"；宏观那个还没改。**照它的先例做，不另发明。**

> ⭐ **2026-08-19 工具盘点补正（比原估更轻）**：数据源的接口**只有一个问题字符串通道**（`fetch(query, timeout)`，见 [data_source.py](../../src/committee/common_context/data_source.py)），而价格源之所以能收外部代码，走的是**构造对象时注入**（`TushareSource(tickers=[...])`），**不是改接口**。
> ⇒ 给宏观源加"查哪个指标"**照此加一个构造参数即可，无需改协议** —— 这一项从"改造契约"降级为"加个参数"。

### 3.1b 分类那一步的处置（**不能简单删**）

盘点发现它今天有**三个**下游，不止路由：

| 谁在用 | 用来干什么 | 换成计划之后 |
|---|---|---|
| 路由 | 决定激活哪些源 | **被计划取代** |
| 资料夹形状 | 决定装进 `ticker_payload` 还是 `macro_payload` —— **两者互斥** | 仍需要这个标签 |
| 早停 | 个股型 + 有确认代码 + 价格冗余组全失 → 产「暂不可分析」并 END | 仍需要这个标签 |

**处置 = 保留标签、取消它的决策权**：标签改由**计划反推**（计划里有没有股票腿）。

**收益**：今天是「分类错 ⇒ 腿断」（问黄金被判主题型 ⇒ 价格源永不激活 = BQ 那笔账的成因）；改完后标签只描述形状，**判错也不影响取什么数** —— 因果链被切断。

⚠️ **必须守住**：分类现有的确定性兜底链（模型失败 → 本地证券名录精确扫描 → 正则 → 兜底，见 [classifier.py](../../src/committee/query_class/classifier.py) 顶部）**不得因换大脑而丢失** —— 坑表 §3.3 明列此项为 🔴。

### 3.2 新数据形态：取数计划

一份计划 = 若干条「取数意图」，每条至少含：

- **查哪个源**（现有五个数据源之一）
- **具体查什么** —— ⭐ v3 按五源探明补齐三格（**时间、条数、研报库选择**），钥匙全表见 §3.2b：
  - 宏观 = 指标编号 + **呈现方式**（原值/同比/环比）+ **期数**（≥6 期才有趋势）
  - 行情 = 证券/资产代码 + 资产类型 + 要哪类数据（价格/估值/财务）
  - 研报 = 中文关键词 + **查哪个库**（5 个报告库 + 资讯流）+ 深度（标题/摘要）+ **取几篇**
  - 新闻 = 中英文关键词 + **时效/站点算子** + **条数**（供给端约 100 条，今天只取 10）
- **为什么查**（一句话，进引用清单当意图标注 —— 这是给另一笔账用的）
- **是主问题还是背景**（两档，供下游区分"针对本问题"与"通用背景"）
- ⭐ **确认留痕**（N2–N5 带来的）：这份计划是**人点头的还是自动确认的** · 用户**改过哪些条目** · **打回重找了几轮**

> ⚠️ **确认留痕是承重字段，不是装饰**：没有它，事后翻归档**分不清"这份资料是人认过的"还是"机器自己放行的"** —— 而这正是本项目最看重的那类区分。同理，回归验证要拿"被确认过的计划"当锚，也得先能认出它是哪一份。

⚠️ **这是一个会流经多个模块的新数据形态**，按坑表要求必须逐一核下游（见 §5 第 3 条）。它至少要经过：资料夹结构 → 断点存档 → 归档 → 追踪渲染 → 引用清单装配。

⚠️ **旧归档必须仍能回放**：新字段一律可缺省，缺字段的旧断点不得崩（坑表 §3.2 首条 + §3.6 同型先例）。

### 3.2c retrieval_planner 的输入（⭐ v3 · 出计划之前，它得先"读过说明书"）

**计划质量的上限，由 planner 读到的工具说明决定。** 光把用户问题喂给它，它不可能知道"宏观要英文词""指标编号配哪个呈现方式""研报检索只排序不过滤所以得多取"——这些全是实测出来的接口脾气，不在任何模型的常识里。

⚠️ **内嵌时要按证据强度分档，别把两种约束混成一句**：「宏观要英文词」是复验过的硬测量（中文 0 结果 + 15–17 秒超时），可以写成硬约束；「研报默认不传时间窗」只有 1 次未复验观测（§3.2b 🔒），只能写成**默认倾向 + 必须回核**，不得写成禁令、更不得被守护测试焊死——否则等于用机器把一条待复验的猜测锁成规则。

三条落地要求：

1. **prompt 里内嵌每个源的「钥匙规格 + 硬约束 + 正反例」**，一手来源 = [seg1_retrieval/](../pipeline/seg1_retrieval/) 五份说明书——它们本来就是按"给 planner 的输入规格"写的（每份的 §3 结构化输入 + §4/§5 正反例）。嵌**浓缩版**（钥匙表 §3.2b + 每源三五条硬约束 + 精选正反例），不是全文照搬。
2. **负例直接用说明书里已实测的失败形态**（撞不上落 CPI / 原句当检索词 / 中文喂英文库 / 截码 / 不消歧），全部逐字来自真实调用——恰好满足坑表第 7 条"样本须取自真实响应"，不许另编。
3. **这是第三个「广告面」**：本仓已有"工具说明 + 参数说明与实现的一致性由守护测试保证"的先例，planner prompt 加入后同理——**说明书改了（DOC-PATROL 巡出源漂移）而 prompt 没动 = planner 拿着过期说明书出计划**，比没有说明书更隐蔽。一致性要么入守护测试，要么 prompt 段落由说明书生成，二选一，不许靠"记得同步"。

> 确认循环（§3.8）里的「打回重找」不需要重读说明书——说明书是稳定输入，变的是用户驳回理由。

### 3.3 三条硬要求（**跟主改动同批，不是后续优化**）

> ⭐ **v2 变化**：加了确认环节之后，第 1 条**不再是为可复现额外付的成本** —— 计划要存下来本就是"确认过"这句话的凭据。**两个需求合成一个。**

1. **计划必须落进断点和归档** —— 既是回放的锚，也是"人确认过"的凭据。位置有现成先例（今天的路由原因就落在那里）。
2. **必须能回放** —— 提供「用归档里那份计划、不重新想」的模式。**两种模式都要留**：只回放会让规划质量退化时没人发现；只自由跑就没法验下游。**被用户确认过的计划天然就是最好的回放锚。**
3. **计划必须进缓存钥匙** —— ⚠️ **这条不做会静默毁掉整件事**：今天缓存的钥匙只有「哪个源 + 问题原文」。同样一句"黄金会怎么走"，上次计划拉 CPI、这次计划改拉黄金期货，**源一样、问题一样 ⇒ 钥匙一样 ⇒ 直接命中旧缓存，拿回还是那条 CPI**。计划改了、数据没改、而且不报错——**正是本方案要治的那个病换个地方复发**。

### 3.5 校验层（本方案的安全支柱）

计划出来之后、执行之前，**逐条过代码校验**（✅ D2 已裁：**存在性 + 格式校验**，不设白名单闸门）：

- 证券代码 → 走既有**名录对账**（保留复用，§3.1）
- 宏观指标编号 → 查数据源里**真实存在**（搜不到 = HTTP 200 + 命中 0，判据按命中数）
- 资产类代码 → **格式须与声称的资产类型一致**（加密 = `币-计价币`、期货 = `=F`、指数 = `^` 前缀……抄[实测 12 格式表](../infrastructure/seg1_retrieval/yfinance-api.md)）——这一刀拦的是**规划员写错格式**；⚠️ **执行期截码那类静默错位它拦不住**（计划期看到的是完好的 `BTC-USD`），由回核层 §3.5b 兜
- 白名单**不当闸门、当建议清单**：常用指标（含默认呈现方式 + 期数）进 planner prompt 与确认界面当参考（§3.2c）；「存在但答非所问」由人工确认（N3）与回核层（§3.5b）兜
- 不合法的条目**单条丢弃并留痕**，不是整份丢
- **全部不合法** → 走 §3.6 降级
- ⚠️ 计划里的字段来自模型，属**宽松字符串喂进严格校验字段**的经典形态 —— 必须在消费点先做归一，脏值只丢那个字段、不丢整条（坑表已记 N≥3 同型，本仓有现成归一函数）

### 3.5b 回核层（⭐ v3 新增 · 执行后按计划对账 —— ✅ D4 已裁：要，与主改动同批）

§3.5 的校验只核**问得对不对**（编号、代码真实存在）。五源探明坐实：**问对了也可能拿回不是你要的，而且全部结构完好、有时间戳、不报错**。所以 ④ 执行后、⑤ 编号装袋前，须逐条按计划回核：

| 源 | 回核什么 | 依据（全部实测） |
|---|---|---|
| 🆕 **全部（第 0 道）** | **先判"这是不是一条错误"** —— 失败常常不抛异常。⚠️ **本道照留** | 2026-08-20 实测：`isError: true` + 错误文本原样回来（`DEFECT-MCP-ISERROR`，✅ **当日已在封装层堵住并 close**）。**但本道不因此撤销**：封装层只护住走它的那条路，而 FRED 搜不到 = 200 + 空 · yfinance 只记日志 · 工具名配错静默回退**一条没变** ⇒ 这是**对所有源的通则**，不是智堡专属 |
| 研报 | 按检索词**回筛相关性**，不相关的降级/丢弃 | 检索只排序不过滤；加时间窗后 20 条仅 4 条对题，其余是铜、锂、澳洲贸易 |
| 新闻 | 回读发布日期 / 来源站点，验算子确实生效 | 算子行为是逆向出来的，无合同保证，可能随时静默失效 |
| 宏观 | 核返回的指标编号 + 呈现方式与计划一致，值非空非 `"."` | 搜不到 = HTTP 200 + 命中数 0；聚合后尾期可能是 `"."` |
| 行情 | **核返回代码与计划代码逐字一致** | 截码后恰好命中另一真实代码（差约 2290 倍、静默）—— 这里是 DEFECT-YF-TICKER-TRUNCATION 的**最后防线** |

三条纪律：

0. 🔴 **回核不通过的条目，必须让它的缓存条目一并失效** —— 今天缓存是**取数成功即写**（[builder.py `_try_cache_set`](../../src/committee/common_context/builder.py) 在 dispatch 内部），而回核排在 dispatch **之后** ⇒ 被判「不是要的货」的数据**已经进了缓存**。不处理的话：同一份计划重跑（用户按 N4 打回重找、或回放模式）会**命中同一条坏缓存 → 跳过取数 → 再次被回核丢掉**，这条腿在整个 TTL 内持续为空且**永远不会重取**，产物里只看得到「腿空」看不到根因。⚠️ 代价按源不同：研报/宏观/A股 1 小时、新闻 10 分钟、**行情 5 分钟**（[intent.py `PROVIDER_TTL`](../../src/committee/facts/intent.py)；智堡不在表里，落 1 小时默认值）——行情那条最危险，回核拒掉截码错资产的价格后，价格腿空可能反而触发早停产「暂不可分析」。
   **两条落地路线二选一，G5 接线时必须显式选**：(a) 回核不通过 → 删除/标记失效该缓存条目后再降级；(b) 把回核**前移到缓存写入之前**（即并进 dispatch，验过再写）。(b) 更干净但要动调度器，(a) 改动小但要新增缓存失效通道。
1. **意图标注打在过了回核的条目上，不打在请求上** —— 一次标成「针对本问题」的研报检索，会把 16 条填充噪音一起盖上「对题」章；BS 的解法只有落在回核之后才不反向。
2. 回核层与校验层同属安全支柱，同样适用坑表第 5 条：**反向变异证明它会拦**（构造一批答非所问的返回，证明会被降级/丢弃）——"跑一次是绿的"不算证据。

### 3.6 降级链（保住今天已有的，不新造缺口）

今天分类那一步的降级链是：模型 → 本地证券名录（确定性、零模型）→ 正则 → 兜底。**这条链不许因为换大脑而丢掉**（坑表 §3.3 明列）。

新的最外层：**规划失败 / 校验全灭 → 退回今天的按标签路由**（D3 建议），并**在产物里留一行字**说明"本次走的是兜底路由"。

⚠️ 留痕方式要照坑表给的通用形状做：**把隐含前提变成产物里的一行字**，而不是在文档里写"记得确认"。

⭐ v3 · **降级判据一律按内容判，不按异常判**：以下三个源的失败**都不抛异常**（⚠️ 这个"三"说的是**失败不报错**，与 §3.5b 需要回核的**四个源**不是同一组，别混读）—— 宏观搜不到是 HTTP 200 + 命中数 0；研报工具名配错会**静默换成发现列表里第一个**（只留一条警告日志）；行情库默认只记日志不抛错。挂在 `try/except` 上的降级链在这三处**永远走不到**，判据要落在命中数、值空、代码不一致这类内容信号上。

### 3.7 预算与超时

- ⚠️ **先核事实**：分类那一步的超时**已经是 15 秒**，而且源文件注释明写「**Phase 0a 有硬边界这个性质已失去**」（[classifier.py](../../src/committee/query_class/classifier.py)）。所以"资料准备段 ≤15 秒"这条老预算线**今天就已经不成立**，本方案**不得拿它当基线**，须重新推导并写明。
- 新增的规划调用**必须用库自带的超时参数**，不许用 Python 并发原语硬控（坑表 §3.2 列了四种"看似生效实则失效"的写法）。
- 顺带一个便宜：这次调用是**串行**发生在八位分析师**之前**的，属于能吃到提示词缓存的少数场景（坑表 §3.2 明确：并行 fan-out 吃不到）。
- ⭐ v3 · **预算的计量单位要从「每源一次」改成「每条计划条目 / 每源总包」**：老的"单源 8 秒"是按一源一调设的，而新能力普遍**一源多调** —— 研报「列表 + 逐篇取摘要」、宏观一题两指标、A 股价格/估值/财务分三接口。**校验计划时应顺手估一次总调用量**（Tushare 官方 500 次/分**仍未压测**；~~智堡配额未测~~ ✅ 2026-08-20 已测 **≈477 次/分不撞限**、2026-08-21 T2 复跑一致，⚠️ 顶未探到、**单日上限未测**）。
- ⭐ v3 · ⚠️ **顺带纠一个容易读反的事实**：行情源自带的重试预算是 15 秒（[yfinance 说明书 §6](../pipeline/seg1_retrieval/yfinance_global_quote_tool.md)），但**管道里到不了 15 秒** —— 调度器对每个源都包了 `wait_for(…, timeout=8.0)`（[builder.py](../../src/committee/common_context/builder.py) `dispatch_sources`），8 秒硬切；探针测到的 13.54 秒是**直调数据源、绕过调度器**的结果。⇒ 重定预算线时**别给行情腿按 15 秒分配**。真正的问题是另一个：**15 > 8 意味着第 2、3 次重试在管道下永远跑不完**（重试逻辑事实上半死），且取消 `to_thread` 并不会杀掉线程（坑表已记）⇒ 失败路径上会留下泄漏线程。~~这两条都该在 G4 顺手核实并决定是调齐两个常量还是显式接受。~~ 🔵 **2026-08-21 改归属（U3）**：G4 第一层没碰它们；现改为**随 U3 那道运行时封顶同批显式定** —— 加封顶本来就绕不开这两件（泄漏线程会被封顶放大，两个常量打架会让封顶算不准），**二选一必须写进 PR，不许沉默继承**。

### 3.8 确认环节（N2–N5 落地）

#### 3.8.1 形态：一个循环，出口只有"用户点头"

```
retrieval_planner 出计划
        ↓
   代码逐条校验            ← 编造的条目在这里被拦
        ↓
   ┌──── 展示给用户 ────┐
   │                    │
   │  ① 确认 ──────────→ 执行取数 → 装资料夹 → 进②段（八位分析师）
   │  ② 自己改某几条 ──→ 改动过同一道校验 ──┐
   │  ③ 打回重找 ──────→ 带上「为什么打回」重跑 planner ──┐
   │                    │                                  │
   └────────────────────┴──────────────────────────────────┘
                （循环，无硬上限，出口只有 ①）
```

#### 3.8.2 复用点：中断/恢复的机器已经有了

不需要新建中断机制 —— 分段跑批已经把整链切成 9 段、段间可停可续（[segmented-e2e-guide](../observations/e2e-runs/segmented-e2e-guide.md)）。**资料准备是第 ① 段，它的结尾正好是现成的段边界**，确认环节落在这里是**顺着现有结构**，不是硬插。

#### 3.8.3 三条实现要求（都不是可选项）

1. **打回重找必须把"为什么打回"带进去** —— 否则规划员会**再给一遍几乎一样的计划**，循环空转还烧钱。用户的驳回理由是这一轮的输入。
2. **用户手改的条目，必须走同一道校验** —— 否则手写错一个代码就绕过了校验直接进资料夹，**等于给安全支柱开了个后门**（这也是 §2.2 D2 备注里那条）。
3. **自动确认按入口区分，不做全局开关** —— 交互使用默认"要人确认"，跑批入口默认"自动"。做成一个全局开关迟早会被忘在"开"的位置上。**且自动确认同样要留痕**（§3.2 那个字段），事后必须分得出哪份是人认的。

#### 3.8.4 边界与风险（诚实标注）

- ⚠️ **段间停点现在是命令行开发用的开关，不是产品级交互**。"内部先用起来"今天就能做；**做成用户真能点的界面是另一件事**，而且[线上跑的还是旧版本](../governance/backlog.md)（BM 那笔账），产品化须单独排期，**不在本方案范围**。
- ⚠️ **循环不设硬上限**（人在回路，人自己会停），但界面上要显示"第 N 轮"；若规划员连续两轮给出实质相同的计划，应提示用户改用"自己改"这条路，避免空转烧钱。
- ⚠️ **自动确认模式 = 今天的行为**（没人把关）。所以**跑批得出的质量结论，不能直接推广到"有人确认"的真实使用**；反过来也一样。两种模式的产物在归档里要能分开统计。
- ✅ **北极星契合**：这一步是**把决定权交还给人**，与"装备决策者、不取代决策者"同向 —— 它不是自动化程度倒退，是把"系统替你决定查什么"改成"系统给你建议、你拍板"。

## 7. 明确不做的（边界 · 防 scope 滑动）

- **不碰交易链路**：本方案只改"取什么数据"，不触及任何决策或资金动作（北极星）。
- **不做"上网搜"这条腿**（✅ D1 裁决 2026-08-20）：本期计划只允许五个正规数据源；计划格式留扩展位（源类型可扩、字段可缺省），将来放开另行裁决。
- **不动引用清单的渲染结构**（BS 的另一半）——本方案只**产出**意图标注，怎么渲染给分析师看是另一件事。
- ~~不动研报取正文（BI）~~ ⭐ v3 订正：**G0b 已探明"取正文"根本不存在**（平台只给摘要）——真实修法是「列表→摘要两步」，已并入 G4b。边界改为：**不做逐篇全量取摘要**（只挑几篇，受配额约束），不接研报之外的四个内容流做常规腿（资讯流仅用于"最近发生了什么"这一类问题）。
- **不趁机调整既有 prompt 的顺序** —— 坑表明确写着：调顺序 = 改变模型的阅读顺序，**不得当"纯格式调整"顺手做**。
- **不放宽任何现有闸门** —— 本方案往"多拿对的数据"方向走，不改任何拦截判据的松紧。
