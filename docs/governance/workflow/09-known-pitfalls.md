## 3. 已知坑 / 防回归 checklist

### 3.1 标记体系（强度 × Status 双维度）

每条已知坑同时带两个维度：

**强度（影响范围）**：

- 🔴 **Hard Block** — 触发即**不得合并**；必须修主路径 / 修 Fallback
- 🟡 **Soft Flag** — 触发**可继续**，但必须记录 `quality_flag` / 入 deferred / PR 描述说明
- 🟢 **Nice** — 不阻塞，建议记录趋势（数据用于 S3 决策驱动）

**Status（当前生效性）**：

- **active**（默认）— 当前仍在生效，需对照检查
- **mitigated** — 已有 fallback / 守护规则兜底，不会再触发，但**保留记录**
- **stale_candidate** — 怀疑不再相关，待子阶段交接审视
- **retired_after_phase_review** — 子阶段交接后明确判定退役

**强度 × Status 矩阵**：

| 强度 \ Status | active | mitigated | stale_candidate | retired_after_phase_review |
|---|---|---|---|---|
| 🔴 Hard Block | 默认 | 有 fallback 兜底，仍保留 | S2 结束后审视 | 子阶段交接判定退役 |
| 🟡 Soft Flag | 默认 | 已观察到不再 flag | 同上 | 同上 |
| 🟢 Nice | 默认 | 趋势已稳定 | 同上 | 同上 |

**已知坑条目格式**：

```
- 🔴 [active] schema 修法不能让旧 _archives/*.json replay 崩
- 🟡 [mitigated] D 类水印硬检查（已加 fallback flag，2026-05-08 起未再触发）
- 🟢 [stale_candidate] 缓存命中率 > 60% 目标（S2.3 已达成，待 S2 结束审视）
```

### 3.2 通用（所有 S2 节点）

- 🔴 [mitigated] schema 修法不能让旧 `_archives/*.json` replay 崩 — 验证：S2.1 Verification Report 139/139 archive replay 全过（2026-05-25）
- 🔴 [active] prompt 修法不能让 LLM 输出突然变结构 — DEBATE_KEY_CLAIMS_CONTRACT / EXECUTION_PLAN_CONTRACT / role prompt 不可覆盖段钉死
- 🔴 [active] 中文 commit message / 注释 / 文档必须 UTF-8 落盘（[docs/governance/git-workflow.md §5](../git-workflow.md#5)）
- 🔴 [active] **「源码里用了 X」这类守护要按 AST 取，别按单行正则扫 —— 换行写法整个看不见**（BK.2 M3 retro 沉淀·2026-09-18）：
  「用了没登记的码 → 红」那道闸原来 `git grep -E 'note_degradation\("…"'`，只认**同一行**上的 `函数(` + `"字面量"`；
  `note_degradation(\n    "code",` 这种多行写法（#304 的 coerced 便条起就是）**从来没被盯住**，而登记漏了正是本域要治的「悄悄」。
  暴露方式 = 两向变异「码表漏登记」**不转红**（[bk2-m3 证据 §3](../../observations/bk2-m3-20260918/FINDINGS.md)）—— 守护全绿、变异才抓得到「守护空转」。
  **规避**：凡「扫源码找调用点 / 读键 / 字面量」的守护，一律 `ast.walk` 找 `Call` 取首参（[test_degradation_notes.py](../../../tests/test_degradation_notes.py) `_note_codes_used_in_source`），
  并给识别器加**自证断言**（至少一个已知的多行调用点必须在结果里）；同族先例 = BJ 派生器「循环读键 / 函数体内 import」盲区（[BJ 拆解](../../plans/BJ-cfg-read-decomposition-2026-09-14.md)）。
  **列文件别丢未跟踪**（#306 review 补·2026-09-21）：扫文件清单要带上还没 `git add` 的新文件（`git ls-files --cached --others --exclude-standard` 或 `git grep --untracked`）—— 本条的范例自己在按 AST 改写时就把 `--untracked` 顺手丢了（`959e9ec` 修），新文件里用了没登记的码照样全绿。
  **判据**：新守护落地时至少做一次「把被守对象改成另一种合法写法」的变异，不转红就是识别器只认一种形态；列文件类守护再加一次「放一个未跟踪的新文件」的变异。
- 🟡 [active] **复用仓内先例，别只抄它的正则 —— 先例常是「正则 + 守卫」一整套**（CRED.1.G3 retro 沉淀·2026-09-09）：
  抄形状不 import，最典型的后果是**排除 / 豁免范围悄悄变宽**，而变宽的方向恰好是闸要堵的那一侧。
  **实证**：审计噪音判据引 [base.py](../../../src/committee/agents/base.py) `_is_noise_number`（裸年份 / A 股代码不算定量主张），
  只搬了年份正则与「6 位」这个形状，**丢了它配套的守卫**（带货币前缀 / 单位或量级后缀 / 小数点 → 不算噪音；6 位还须 A 股板块前缀）
  ⇒「1920 美元」「118000 万元」被当噪音吃掉，闸在自己要堵的形态上漏；注释还写着「同 base._THESIS_YEAR_RE」，读起来像已对齐。
  **规避**：能 `import` 就 import 常量与判据函数（本轮修法即如此）；写「同 X」之前先把 X 整段读完、核对差异；
  **连带一条**：同一文件里可能已有更贴的那份判据（本例 `_LEGAL_STAMP_RE` 认裸 core + 大小写漂移，比借来的免打标区正则全）——
  选复用对象时先问「这份判据当年是在什么输入前提下写的，我这里的输入满足吗」。
  **出处**：[retro CRED-1.G3](../../retro/S2/CRED-1.G3_2026-09-09.md)（PR [#284](https://github.com/JunoChenZt/subagent-for-investment/pull/284) 合并前 review 5 条里 2 条同此根因）。
- 🟡 [active] **影子 / 观测类机制不得走会改变被观测对象输入的通道**（CRED.1.G2 retro 沉淀·2026-09-10）：
  「影子对账」「WARN 试用」「只记录不拦」这类东西的价值全在**被观测对象不知道它存在**。把它当普通 finding 塞进现成管道，
  管道另一头往往接着决策者的提示词 / 回应 pass / 豁免集 —— 观测器就变成了输入，样本从此不干净。
  **实证**：`G1-shadow` 首版走正式 `RiskGateFinding` 通道 → 自动进 fund_mgr 预检段 + 逐条回应 pass + 打码豁免数字集
  （PR [#285](https://github.com/JunoChenZt/subagent-for-investment/pull/285) review 抓出·十修第 1 条）。修 = `is_shadow` 标记 + `llm_facing_findings` **一处过滤**所有 LLM 消费面，事件 / 断点 / 归档 / trace 照带。
  **规避**：新增影子 / 试用类产物时，先列出该通道的**全部下游消费面**，逐个问「这一面看见它会不会改变行为」；会的一律隔离。
  **连带（同 goal 第二课·observe·N=1）**：设计 pass 的「现状」段只核了闸门代码那一行，**没核登记表今天还会不会出现那种形态**
  —— 一手材料要核到**数据形态**那一层，不止代码那一行（本例：两种错误登记形态在今天的表①里都不可达，识别器实际域 ≈ 历史归档）。
  **出处**：[retro CRED-1.G2](../../retro/S2/CRED-1.G2_2026-09-10.md)。
- 🔴 [active] **守卫要锚在它真正要守的那个对象上 —— 「差不多的位置 / 差不多的配置」= 守了个寂寞**（CRED.1.G4 retro 沉淀·2026-09-10）：
  守卫（免检条件 / 资格判定 / 独立性检查）写出来都像回事，但**判据锚错对象时，两个方向会同时坏**：
  该拦的漏过去、不该拦的被拦住 —— 而测试若只覆盖"典型例子"，两边都看不见。
  **实证 A（锚错位置）**：年份免检的价位守卫拿**整句** `search` —— 「the 2026 midterm election, shares closed at **$180** that day」里
  那个 `$180` 把**真年份 2026** 拉回比较，**正好让本节点要治的那条 G7 误报复活**；反过来「index closed at 2000」这种
  值域内的指数点位因为整句没有单位词，又被当年份放过。修 = 先在原文里**定位登记值本身**，只看它紧邻的前后窗口；定位不到 → 走拦侧。
  **实证 B（锚错配置）**：「复核模型必须与产出方不同家族」这道独立性守卫，比的是 `ANALYST_MODEL` / `DECISION_MODEL` 这几个
  **tier 兜底常量** —— 而线上每个角色都走 `model_for_role` 单独配，`.env` 里 `COMMITTEE_MODEL_BEAR=gemini-2.5-pro` 就是未注释实配 ⇒
  守卫在真实配置下会说"独立"，实际是同一家模型给自己背书。修 = 比**产出该 fact 的那些角色的 per-role 实配**（`cited_by_roles` →
  `ROLES[k].model`），不知道谁写的就把全部候选算进来。**连带**：`oc/<model>` 这种"换网关不换模型"的前缀必须**先剥再归族**，
  否则同一个模型换个写法就骗过守卫。
  **规避（写守卫时逐条自问）**：① 我的判据 evaluate 在**哪个对象**上？是不是把"这一句里有"当成了"这个数字旁边有"？
  ② 我比的是**运行时真正生效的值**，还是某个默认/兜底常量？③ 同一实体有没有**别名写法**（前缀 / 大小写 / 网关包装）会绕过判据？
  ④ 两个方向各写一条靶测：**该守的守住** + **不该守的别误伤**。
  **出处**：[retro CRED-1.G4](../../retro/S2/CRED-1.G4_2026-09-10.md)（PR [#286](https://github.com/JunoChenZt/subagent-for-investment/pull/286) 合并前 review 十条里 3 条同此根因）。
  与「复用先例要连守卫一起抄」（2026-09-09）同族：那条是**守卫没抄全**，这条是**守卫锚错对象**。

- 🔴 [active] **AI 判定要朝「放行」方向影响承重闸，必须同时满足三个可机检前提，且最多撤到「存疑」档**（CRED.1.G4 retro·red-line should_update·用户 2026-09-24 节点收口裁 adopt；裁决本身 = 2026-09-10 D4-b）：
  「只降不升」是 G5 誊写核查焊死的方向；第一次显式越过它的是 check① 硬拦的异模型复核（该硬拦历史 5 响 5 误报 0 真错）。**再有人提「叫个 agent 看看是不是误报」时照本条办，不重走辩论**。
  **三前提（缺一不可·须焊在代码里、不是写在注释里）**：① 复核模型与产出方**不同 provider 家族**（比的是运行时 per-role 实配、别名 / 网关前缀先归一 —— 首版比的是 tier 兜底常量、`oc/` 前缀让同一模型判独立，两道都空转过）；
  ② 复核输入**只含被审事实 + 出处原文**，不含推理、决策与其它 finding；③ 输出**封闭三选一**，且只有一个字面能放行。
  **撤到哪**：只到**带人读标记的中间档**（计划保留 + 存疑标 + 质检 Q8 WARN + trace ⚠️），**永远不给「干净放行」的代码路**；G5「只降不升」仍然有效、与本条互不读。
  **冒烟必须两向**：已知误报（期望撤）+ 真错（期望不撤）—— 只有一类样本时「永远说误报」也能满分。
  **现状读数（2026-09-24）**：自然跑批里复核员被叫到 1 次（09-17 NVDA·「13 万」↔「130,000」量纲误报·判对并撤到存疑），**自然真阳性 0**；真错侧至今只有合成样本。
  **出处**：[retro CRED-1.G4](../../retro/S2/CRED-1.G4_2026-09-10.md)（PR [#286](https://github.com/JunoChenZt/subagent-for-investment/pull/286)）· 节点收口 [retro CRED](../../retro/S2/CRED_2026-09-24.md)。

- 🟡 [active] 新节点不要绑死单一 LLM provider — 走 `model_for_role()` 路由；例外需 PR 描述说明
- 🔴 [active] 不做 cloud routine / 远程定时任务，所有延迟任务一律本地 `scheduled-tasks` 跑
- 🔴 [active] **"看似正确实则失效的隔离 / 超时机制"识别清单**（A6.1.1.2 retro 沉淀）：
  以下模式在 Python 中**看似生效实则失效**：
  1. `with ThreadPoolExecutor(...)` + `future.result(timeout=X)` — `__exit__` 调 `shutdown(wait=True)` 等所有 thread 自然结束，timeout 不限制总执行时间（Python thread 不能 kill）
  2. `signal.alarm(X)` — 只在主线程生效，无法限制子线程
  3. `subprocess.Popen(...)` + `communicate(timeout=X)` — timeout 只覆盖 `communicate()`，不覆盖 Popen 内部其他阻塞调用
  4. `asyncio.wait_for(coro, timeout=X)` — 若 coro 内部有同步阻塞 I/O，timeout 不生效（CPU-bound 同步代码 GIL 抢占同理）

  **防御原则**：
  - 网络层超时优先用 library 自身参数（如 langchain BaseChatModel `timeout` 透传到 HTTP socket，真中断网络调用）
  - 不要靠 Python concurrency 原语强制限制不可中断操作
  - 任何"超时机制"都需写"超时失效"反向单测验证（mock 一个 hang 2× timeout 的 invokable，断言 caller 在 1× timeout 内返回；不只是测"超时 exception 被抛"）
- 🔴 [active] **git worktree 跑测试 / e2e 必须确认 import 的是 worktree src**（R-5 修复 2026-06-15 沉淀）：
  项目走 editable-install（`pip install -e`，.pth 指向主 repo src）。在新 worktree 改了代码后直接
  `pytest` / `python -m committee.cli`，import 的仍是**主 repo 旧代码**、非 worktree 改动——测/验全绿
  是**假绿**（一行新代码都没被测到，比没测更危险）。同理失败的 check 也可能是**假阴**（preflight 漏
  import config 没载 .env → 假性 auth fail）。
  **防御**：worktree 跑任何测试/e2e 前 `PYTHONPATH=<worktree>/src` 顶最前；先验证
  `python -c "import committee.X; print(committee.X.__file__)"` 指向 worktree、或断言一个已知改动的行为
  （改了返回值的函数返回新值）。**绿了先问"测的是不是我改的代码"；失败的 check 先查根因不照单全收。**
- 🔴 [active] **真值源可能尚未合入 main·须查未合分支**（层② EXEC-FLOOR 相位2a R6 事故沉淀·2026-07-07）：
  handoff / 交接单点名的"真值源"设计文档在 main 找不到时，**先 `git branch -a` + `git ls-tree <branch> <path>`
  查未合分支**，不得因"main 上没有"就判"待建 / 不存在"跳过。本次因此误读旧设计、白烧一版实现（路B）再
  返工（路D）+ 拉用户重新推导。是 R6「从 main tracked 读」的**反向盲区**（真值源可能在分支上、尚未进 main）。
- 🟡 [active] **改动引入"流经多模块的新数据形态"须逐一核下游处理器 + 相邻/守护注释**（M1-T11 两轮冷审 N=2 → M1-T4 冷审 N=3 沉淀·2026-07-09）：
  一次改动引入会**流经多模块的新标记 / 新字段 / 新枚举值**时，节点收口**必须显式列出"哪些现有的文本 /
  数据处理器会遇到它"并逐一核**——别只测直接改的地方。出处：T11 新标记族 `[W#…]` 两轮冷审各命中一处
  下游未跟上（audit / 散文处理器）。共性 = 只顾"直接改的地方"、忘了"新东西还会流到哪些没改的地方"。
  **N=3 扩展（M1-T4·2026-07-09）**：核的范围**不止代码处理器·还含注释 / 文档**。T4 让外源进
  `references_appendix`（表③）时，改了 `_build_references_appendix` 主注释、却漏了**相邻字段
  `web_citations` 的注释**（仍写"references_appendix gate 会读·外源永不进"·与新事实矛盾）——冷审
  抓到。**动作**：改数据形态 / 字段语义后，`grep` 该数据流经模块里**引用它的注释 + 设计文档**（不只
  `grep` 调用它的代码），相邻字段注释 / 守护注释一并核（R5「拿注释当设计一手源」会踩·stale 注释误导后人）。
  共性升华 = "守护项 / 相邻模块 / 相邻字段注释不改 ≠ 不受新数据形态影响"。
  **N=4 扩展·新子型「相对不变式被静默倒挂」（classify 超时 PR #210 冷审·2026-07-24）**：前三次
  都是**注释变 stale**（描述旧行为·误导后人）；本次是**注释里编码的"相对不变式"被打破**——
  `TICKER_RESOLVER_SEARCH_LLM_TIMEOUT_SECONDS = 10.0` 注释写 *"比非搜索的 2.5s 宽——一轮要读完
  search 结果再回 JSON"*，主路径 `LLM_TIMEOUT_SECONDS` 由 2.5 调到 15 后 **10 < 15**，
  「search 路径应更宽」这条**设计性质真的不成立了**（不只是文字过时：更费时的路径反而拿到更紧的
  天花板）。**两者区别决定修法**：stale 文字 → 改文字即可；**相对不变式被破 → 必须显式裁决
  「跟调 or 有意不跟调（写明为什么）」，且优先改成结构化绑定 + 守护测试**，让它不可能再静默倒挂
  （本次修法 = `max(10.0, LLM_TIMEOUT_SECONDS)` + `test_search_timeout_not_tighter_than_main`·

      O 的触发条件是「S2 阶段完成」而 S2 已 ~100%，实为离触发**最近**的一条。
    - **守护 fixture 停在旧形态**：BH 的渲染守护 fixture 仍是修复前的字符串形态 → 真缺陷
      （对象数组被渲染成 `[object Object]`）**被 fixture 罩住、CI 一路绿**。
    - **第三方库的归一层悄悄改了字段名 —— 我们读的那个名字被填成恒 0**（2026-08-11 AG.1 实测 · N=7）：
      `langchain-anthropic==1.5.0` 归一 Anthropic 返回时，把缓存**写入量**拆进
      `ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`，而我们读的 `cache_creation` **恒填 0**
      —— 同一次响应里原始 `cache_creation_input_tokens=5520`、归一后 `cache_creation=0`。
      后果：成本少算 20%，且「打的标记生没生效」这条判据**永不会响**。
      ⚠️ **与前三个实测的分界**：那三个坏在**我们自己写的**检查/守护代码里；本例我们的代码逻辑无误，
      **坏在两者之间的第三方归一层**——版本一升就可能悄悄换字段名，而**没有任何测试会因此变红**
      （单测喂的是我们自己造的 payload，永远是旧字段名）。
      **防御（本形态专属）**：凡是判据依赖**第三方库归一后**的字段，落地时必须
      ①拿一次**真调用的阳性样本**证明它会响（不是构造 payload——构造的用的正是你以为的那个字段名）；
      ②把那次真实返回的**原始形状**固化进测试 fixture，让日后升级库时形状漂移会被抓到。
      出处：[AG.1 验尺子](../../observations/ag-cache-meter-probe/EVIDENCE.md)。
    - **测的是"这条路会降级"，而环境里还有别的路也会降级 —— 测试绿的是另一条路**
      （2026-08-21 seg1 **G2** 反向变异 M1 当场实测 · **N=8**）：
      新写的测试要证明「源认不出指标 → 整条腿降级」，**却没有 mock 上游**。
      于是 `degraded` 其实来自「拿假 key 真去请求 FRED 失败了」——
      **把修法整个退回去（认不出仍静默落 CPI），这条测试照样绿**，而且还在测试套件里打真网络。
      ⚠️ **与本形态前几个实测的分界**：那几个坏在检查代码 / fixture / 第三方字段名上；
      本例**测试代码本身写得对**，坏在**被测系统有多条通往同一结果的路**，
      而测试没堵住其他那几条 ⇒ 观察到的结果无法归因。
      **防御（可直接照做）**：验"某条路会产生结果 X"时，**先把所有其他能产生 X 的路堵死**
      （本例 = 把上游 mock 成必定成功，那样 `degraded` 就只可能来自那条认不出的路）。
      **自检问法**：如果我把要验的这段逻辑整个删掉，这条测试会不会还是绿的？
      —— 答不上来就等于没验。**这个问法只有跑反向变异才答得准**，光读代码答不出（本例就是读代码时没看出来）。
      出处：[G2 冒烟与真 API 验证](../../observations/rp-g2-smoke-20260821/FINDINGS.md)。
    - **判据锚在一个"语言上不可能出现"的形态上 —— 它不是很少响，是永远不会响**
      （2026-08-21 seg1 **G2 冷审**实测 · **N=9**）：
      G2 写了一条全仓守护「不许有自动取第一条搜索候选的代码」，用正则扫
      `search_series(...)[0]`。但 `search_series` 是 **`async`** 的 ——
      不 `await` 就下标，运行时直接 `TypeError: 'coroutine' object is not subscriptable`。
      ⇒ **该正则唯一能命中的形态，是一段必崩、因而永远不会被提交的代码**；
      真正顺手的两种写法（`(await search_series(...))[0]` 和「先存变量、下一行再取下标」）
      **它全部 MISS**。**实证**：在源码里种下一个真违规，旧正则命中 **0** 条、
      新检测器当场点名到行。
      ⚠️ **与前几个实测的分界**：那些坏在"信号来源不对 / 归因不清"；
      本例坏在**判据描述的那个字符串在该语言里根本构不成可运行的代码** ——
      测试写得像在检查，实际在检查一个空集合。这类最难看出来，因为
      **正则读起来完全正确**，错的是它与被测语言的语义不相容。
      **防御（可直接照做）**：
      ①**判据要锚在"能跑起来的那个形态"上**——被测对象是 async 就锚 `await X(...)`，
      是 context manager 就锚 `with X(...)`；写完先问一句「我扫的这个字符串，
      放进代码里跑得起来吗？」跑不起来 = 判据是空的。
      ②**给检测器配正反样本自证会响**：几条已知违规写法必须被它抓住、几条正当写法
      必须不被误报，两组都进测试。少了这组，"全仓零违规"既可能是真干净、
      也可能是检测器认不出任何东西。
      ③**扫描类守护再加一道"扫到了几个文件"断言**：扫到 0 个 = 守护在空转
      （函数被改名/挪走），**空转的守护比没有守护更坏**——它会一直绿，而人以为有人看着。
      出处：本条守护的修法见 `tests/test_common_context_sources_fred.py`
      的 `_auto_pick_offenders` 及其两组正反样本。

    变异样本**优先用合成构造**，不要锚在会被 close / 重命名 / 改写的真实对象上；

  (b) **判据的名字 ≠ 判据量的东西**。引用某条检查作为"这块已覆盖"的依据前，先确认它对**你关心的那个形态**有判别力

- 🟢 [active] **设计 / 改 prompt 时，多次调用共用的内容排在最前，每次都变的排在后面**（2026-08-11 立·成本向·不影响正确性）
  **机理**：各家服务商的 prompt 缓存都按「**从第一个字起完全一致的最长开头**」计价 ——
  遇到第一处不同就断开，后面即使一模一样也不再享受折扣。所以**共用内容排在哪，决定了它能不能被复用**，
  不是"内容重复就自动省钱"。
  **现状实测（[归档 run seg9](../../observations/regression-e2e-20260730/run-NVDA-zh-20260730/seg9-decision.checkpoint.json)·162 次调用·输入合计 70 万 token）**：
  - 八位分析师的排法是「**各人专属的角色指令（实测 2,421–7,885 字符，各不相同）在最前**」→
    「八人一字不差的输出格式说明（实测 **4,260 字符**）在后」→ 本次问题 → 共用数据来源块
    （拼装见 [prompts/analyst/\_\_init\_\_.py](../../../src/committee/prompts/analyst/__init__.py)、
    [agents/base.py `make_analyst_node`](../../../src/committee/agents/base.py)）。
    最不一样的排在最前 → **跨角色共享长度 = 0**，那 4,260 字符共用说明一次也没被复用过。
  - 同一角色自己多次调用（返工 / 扩写 / 多轮）仍能命中：DeepSeek 自动前缀缓存实测 60–75%。
  - 贵模型（Anthropic / Gemini）需**显式标记可缓存断点**，全仓一处未打 → 命中率 **0%**。
  - ⚠️ **但"打上标记"不等于"就能命中"——本坑最反直觉的一半（2026-08-11 拆解现场核实）**：
    贵模型那侧的缓存**从整段最前面按顺序匹配（角色指令段 → 对话消息）**，
    所以**只要最前面那段换了，后面即使逐字相同也全部作废**。实证：决策环节两次大调用
    （提纲 1.59 万 token + 定稿 2.23 万 token）**共享一大段相同的正文材料**，
    但两次用的是**两份不同的开头指令**（[base.py:2961](../../../src/committee/agents/base.py)
    与 [base.py:3372](../../../src/committee/agents/base.py) 各喂一份）→ 前缀在第一段就断，
    **打再多标记也接不上茬**。要吃到这笔，必须动调用结构（对齐两次调用的开头段），
    那已经不是"只打标记"，属另立一期的活。
    **教训**：估算缓存收益时，先确认"共用内容前面还有没有会变的段"，
    别只看"这段内容重复出现了几次"。
  - 🔴 **本条最要紧的一半：并行发出的一批调用之间，共享前缀根本吃不到 —— 而并行是本仓默认写法**
    （2026-08-11 A/B 实测坐实 · [证据](../../observations/ag-prompt-order-ab/EVIDENCE.md)）。
    缓存要生效必须**有先后**：先有一次调用把开头写进缓存，后来的才读得到。
    八个 analyst 是**同时**发出的，谁都不在谁之后 → 共用前缀再长也命不中。
    **实测**：把共用段（4,260 字符）从尾部提到最前、文本一字未改，
    八个角色**首次调用的命中量两臂全部为 0、一个不差**；整段命中率反而从 28.9% 微降到 26.3%
    （那 5.8 万命中自始至终来自**同一角色自己的第 2、3 次调用**——那些才是串行的）。
    ⚠️ **所以本条规矩要读成两句**：共用段排最前 **①对串行调用有效**（重试、多轮、同一角色连续调用）；
    **②对并行 fan-out 无效**，改排序是白费力气——要吃到得先改成串行，那是拿并发换缓存、通常不划算。
    **判据**：动手前先问"这批调用是一个接一个发的，还是一起发的"——一起发的就别指望跨调用共享。
    **连带（同次实测的次要发现，未达结论）**：重排后八份报告七份正文变短、部分近腰斩，
    结论分布从均衡偏向看多——单跑一对不构成结论，但足以说明**"只换顺序不改字"并不等于对产出无影响**，
    真要做仍须按 §3.2「改 prompt 要看形态变没变」走完整 e2e 对比。
  **规避**：新写 / 重构 prompt 时就把共用段放前面 —— **新写时是零成本，事后再调不是**。
  ⚠️ **反向约束（防"顺手优化"）**：现行顺序是历史遗留、不是刻意设计，但**调整既有 prompt 的顺序 =
  改变 AI 的阅读顺序**，不得当"纯格式调整"顺手做 —— 属触及核心链路，须走完整拆解 + 全链 e2e 对比验证。
  **出处**：[backlog AG](../backlog.md#ag-全链路-kv-cache--prompt-caching-优化2026-05-29-记录)（cache 优化）讨论期实测；

### 3.10 已知坑维护协议（只增不减）

**核心原则**：S2 周期内 known pitfalls **默认只增不减**。known pitfall 的价值不是"当前一定还会发生"，而是"防止 S2 内重复踩坑"。

**允许的操作**：

- 新增坑（通过 [07-retro-goal.md §2.10](07-retro-goal.md#210-goal-级-retro按需) must_update 触发）
- 补充触发条件
- 补充规避方法
- 修改 status（active → mitigated）
- 标记适用范围缩小
- 升级强度（🟢 → 🟡 / 🟡 → 🔴）— 仅当连续多次 retro 命中或观测期数据驱动

**禁止的操作**：

- 直接删除坑
- 将坑从 🔴 Hard Block 降级为不存在
- 删除历史原因和触发证据
- 在 S2 周期中途批量"清理"已知坑

**删除规则**：

- S2 周期内**原则上不删除** known pitfalls
- 仅在子阶段交接（[10-verification-report.md §4](10-verification-report.md#4-verification-report-触发点) Verification Report 触发）或 S2 结束复盘时统一审视
- 删除必须有 PR 描述说明 + 替代证据 + 用户确认
- 推荐用 **status = retired_after_phase_review** 替代物理删除

**为什么不删除**：

- 历史证据保留 → 后续 retro 可引用
- 防 agent 为了清爽文档把还没充分验证的坑删掉
- 子阶段交接审视 → 系统性回顾，比中途零散删除更稳

### 3.11 pitfall-scout subagent 工作方式

`pitfall-scout` 是 **subagent 化 skill**（通过 Task tool 派遣，详见 [skill-design.md §3.1](../skill-design.md#31-pitfall-scout)）。主对话 Claude 在节点起步前调用，subagent 读本文档 §3 全表（约 400 行），返回 3-5 条相关坑。

**为什么 subagent 化**：§3 全表 ≈ 400 行；主对话直接读会消耗大量 context。subagent 隔离后只返回结构化 alerts（< 30 行）。

**输入**：

- 任务描述（自然语言）
- 子阶段（S2.1 / S2.2 / S2.3）
- 涉及的文件 / 模块 / 节点 ID
- `<goal>` XML（若已拆解）

**输出 schema**：

```xml
<pitfall_alerts task_ref="<task-id 或 goal-id>" subphase="S2.1|S2.2|S2.3">
  <scanned_sections>
    <section>§3.2 通用</section>
    <section>§3.3 S2.1 召回层</section>
  </scanned_sections>
  <alerts count="3-5">
    <pitfall ref="§3.3" severity="🔴" status="active">
      <pitfall_text>Query Classification LLM 必带 regex / macro_event fallback</pitfall_text>
      <relevance>本 goal 改 facts/cache.py,触发"缓存层 WAL 模式"约束;若同时改 query_classification 必须保 fallback</relevance>
      <action>改动前 grill cache.py 的 WAL 实现 + 确认 fallback 链未断</action>
    </pitfall>
    <!-- 3-5 条 -->
  </alerts>
  <skipped_irrelevant>
    <section ref="§3.7">S2.2 D/E/F 类规则 — 本任务在 S2.1,跳过</section>
  </skipped_irrelevant>
</pitfall_alerts>
```

**约束**：

- subagent **不修改本文档**（must_update 落盘是 `retrospective-goal` 职责，详见 [07-retro-goal.md §2.10.7](07-retro-goal.md#2107-must_update-的落盘)）
- alerts ≤ 5 条；超过 = 任务范围过大，建议先拆任务再扫
- 若 §3 对应子阶段表为空（如 S3 / S4 未启动）→ 输出空 alerts + 标注"该子阶段坑表未建立"
- subagent 无状态：每次任务起步重新调用，不复用前次 context

**下游消费**：

- alerts 进入 `<decomposition_input><pitfall_alerts>`，详见 [03-decomposition.md §2.4.7](03-decomposition.md#247-decomposition_input--decomposition_output-包装-schema)
- 每条 alert 的 `<action>` 必须**落地到** `<goal><stop_conditions>`，不能丢
