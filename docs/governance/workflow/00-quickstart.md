## 1. 接入片段（复制进 `CLAUDE.md` / `AGENTS.md`）

> **通用版真值源在 [core/01 §0](../../../core/01-entry-and-routing.md)**（指向骨架文档 + project-config 槽位）。下面这份是**实例层版**，指向本目录的子文档编号，两份内容同义。项目自己的红线、北极星、阈值在 [project-config.md](../../../project-config.md)。

```markdown
## 过程规则（真值源 <workflow-root>/../workflow.md，按阶段只读对应子文档，不通读）

1. 接到任务先定档 S / M / L（01 §2.2.5）：先判是不是大任务（01 §2.1 七条），是则判风险（01 §2.2 五条）；非大任务再过 S 判据五条（≤3 文件 / ≤100 行 / 不碰敏感路径 / 不新增能力依赖 / 有现成验证），全满足才是 S。档位写一行进交付单头部；只许升不许自己降；DoD 前按实际 diff 对账，超了自动升档。拿不准 → 高一档。L 档先给我拆解方案，我确认后再动手。
2. 按档位矩阵（01 §2.2.5.3）做：S = 执行 → 自验 → 8 问 → 简版 DoD → 交付单，不拆解不写 XML；M = 拆成 `<goal>`（03 §2.4.3）+ 全 DoD + 5 类 evidence；L = M 全部 + 用户确认 + 节点复盘 + 完整 PR。矩阵不要求的写「本档不要求」，要求但没跑的才是 ⚪。
3. 每个 goal 做完按序走：跑 `<verification>` + 写自验报告（04 §2.6）→ 刹车 8 问（05 §2.7，任一"是 / 不确定"就停下问我）→ DoD 四步（06 §2.8）→ 收 evidence（06 §2.9）。
4. DoD 每一步只有三态 ✅ / ❌ / ⚪（06 §2.8.0）。没跑必须标 ⚪ 并写四种原因之一；能跑没跑不是 ⚪，是盲跑。有 ❌ 不许交付；有 ⚪ 可以交付但由我决定收不收。
5. 交付一律用三栏交付单（06 §2.9.5）：改了什么 / 验证了什么、怎么验的 / 未验证什么、为什么。第三栏没有就写"无"，不许空着；第三栏非"无"时全文不许写"全部通过"。
6. 项目红线（见项目指令）任何时刻触到就立即停，不等上面任何判定。
7. goal 有返工、触发过刹车、暴露过意外坑、改过 case、高风险节点 —— 任一为真跑 goal 级 retro（07 §2.10），否则跳过。
8. 节点收口：retro 5 问（08 §2.11）→ PR 描述按 08 §6 模板（里面已内嵌 DoD 三态 + 交付单）。
9. 踩到坑先查坑表（09 §3）有没有登记；新坑回填坑表，不是加新流程。
```

## 2. 什么时候读哪一份（压缩版）

## 3. 完整案例

[examples/walkthrough-cli-json-flag.md](examples/walkthrough-cli-json-flag.md) —— 从用户一句「给 report 子命令加 `--json` 输出」开始，走完判定 → 拆解 → 执行 → 自验 → 刹车 → DoD 三态 → 交付单 → retro 判定 → PR 描述，每一步给出**实际写出来的那段东西**，不是描述。案例里冒烟那一步故意是 ⚪ 未验证（环境无 API key），用来演示第三态怎么写、怎么交付。

## 4. 这份文档不做什么

- 不替代任何子文档的规则。接入片段里的每一条都是指针，规则本体在子文档。
- 不替你定项目红线、北极星、验收阈值。那些在 [project-config.md](../../../project-config.md)（评审建议 1 已落地：骨架 [core/](../../../core/README.md) + 配置分离，见 [workflow.md §7.5](../workflow.md#75-文档迭代历史非完整)）。
- 不解释为什么要这么设计。要看动机读各子文档开头的「治的是什么」。
