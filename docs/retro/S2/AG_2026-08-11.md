## 一、AG.2 goal 级复盘

```xml
<retro_goal id="AG.2" timestamp="2026-08-11">
  <triggered_by>
    <condition n="2">刹车 Q7 命中（真机冒烟产生费用 $0.11）+ Q8 命中（默认开 / 默认关是两个合理方案且影响后续路线）</condition>
    <condition n="6">属高风险节点（拆解判定阶段一整体高风险）</condition>
  </triggered_by>

  <tldr>
    贴标记这段代码本身很小（一个 helper + 两处接线）。真正需要判断力的是「默认开还是默认关」，
    而这个答案只有把账算到**单次调用粒度**才拿得到：三次贵模型调用里只有一次够格贴标记，
    而那一次在单跑一次分析时**没有第二次去读它**。据此算出临界命中率 21.7%，得出「默认关」。
    教训一句话：**「能省 89%」是命中时的数字，决定默认值的是命中率，不是省幅。**
  </tldr>

  <journey>
    <phase name="切口选择">
      先 grep 全部 SystemMessage 构造点，确认所有 Anthropic 流量都收在 `_invoke_json`
      一个函数的两处（首发 + 重试），风险闸也走它。一处收口不漏，比散在各调用点安全得多。
      pass0 / 辩论那些自建 SystemMessage 的地方全是 deepseek，本就不在范围内。
    </phase>
    <phase name="按实例判，不按模型名判">
      本仓有一条聚合端点路（`oc/` 前缀 / `COMMITTEE_FORCE_OPENAI_COMPAT`），
      那条路上跑 claude 模型名时用的是 `ChatOpenAI`。按名字判会把标记贴到不认识它的端点上。
      靶测专门写了这一条（`test_openai_compat_running_claude_name_not_marked`）。
    </phase>
    <phase name="默认值的取舍 —— 本 goal 真正的判断点">
      拿归档跑批的逐次调用记录算账：贵模型 3 次调用占整单 66%，但其中
      只有 `fund_mgr_decide` 的开头指令（7,236 字符）过得了 2,048 词元门槛；
      另两次（678 / 411 字符）贴了也被静默忽略。而 `fund_mgr_decide` 一次跑批只发生一遍。
      → 单跑一次 = 只写不读 = 净亏 $0.021；命中时省 $0.0745。
      → 临界命中率 = 0.0207 / 0.0952 ≈ **21.7%**。生产以单次分析为主 → **默认关**。
    </phase>
  </journey>

  <mistakes>
    <mistake>
      <what_went_wrong>
        上一轮回复以「开始了」收尾，但那一回合**没有任何工具调用**——把「宣布要做」当成了「做了」。
        用户下一句问「如何」，我才发现自己什么都没干。
      </what_went_wrong>
      <fix_or_lesson>
        表述动作的句子（「现在开始做 X」）必须与**同一回合内真的开始做 X** 绑定；
        若这一回合不打算动手，就说「下一步做 X，要我现在开始吗」，不要用完成时/进行时的语气。
        这不只是措辞问题 —— 用户据此以为工作在推进，实际停滞了一整轮。
      </fix_or_lesson>
    </mistake>
  </mistakes>

  <techniques>
    <technique>
      <pattern>
        回答「某个开关默认开还是默认关」时，算**临界点**（多高的命中率才划算），
        而不是拿「命中时能省 X%」当理由。省幅和命中率是两个数，只有前者时无法决策。
      </pattern>
      <when_to_apply>
        任何「有收益但也有固定代价」的开关：缓存、预取、预热、投机执行。
      </when_to_apply>
    </technique>
    <technique>
      <pattern>
        改动落在**唯一入口函数**上，而不是散在各调用点。判定逻辑集中一处 →
        靶测能穷举分支，且「有没有漏一处」变成可验证的问题（本例用 spy 断言首发 + 重试都经过）。
      </pattern>
      <when_to_apply>
        横切关注点（鉴权 / 计量 / 缓存 / 脱敏）接进既有链路时。
      </when_to_apply>
    </technique>
  </techniques>

  <proposals>
    <observe>
      <signal>
        以「开始做 X」收尾却没有在同一回合动手，导致用户以为工作在推进。N=1。
      </signal>
      <why_insufficient>
        单次。若再出现 2 次同类（宣布动作与实际执行脱节），升级 should_update，
        考虑写进沟通风格约定。
      </why_insufficient>
    </observe>
  </proposals>

  <quality_self_check>
    <must_update_count>0</must_update_count>
    <is_trivial>false</is_trivial>
    <retro_should_have_been_skipped>false</retro_should_have_been_skipped>
  </quality_self_check>
</retro_goal>
```

## 三、一句话总结

**这个节点没省到钱，但修好了用来判断有没有省到钱的那把尺子** —— 而那把尺子此前每次少算 20% 的成本，并且会让「优化生没生效」这个判据永远不响。原条目设想的三条路里，两条被实测证伪（并行调用吃不到共享前缀），一条落地但默认关（单跑一次是净亏）。真正值钱的那条（省 11%）超出了 backlog 该管的范围，已剥离为 S3 任务。
