## 0. 核心原则（任何阶段都不越线）

### 0.1 北极星裁决原则

**装备决策者，不取代决策者。**

❌ 自动下单 / 自动调仓 / 无人确认的交易执行
❌ 长期记忆 / AI 投顾业务化

✅ 执行计划（数字 + 锚定 + 来源）
✅ 风险触发器 / 再评估提醒
✅ 组合影响分析 / 历史决策对比

### 0.2 工程稳定性原则

**稳定能跑 > 质量。** 单 run 总延迟硬上限 = **90s**。

```
Priority 1: 整 run 不崩溃，永远产出最终报告（即使是 degraded report）
Priority 2: 单组件失败有明确 fallback
Priority 3: 多层 fallback 嵌套时仍有最终兜底
Priority 4: time budget 硬上限保证用户体验
Priority 5: 质量保证机制是改善方向，不是阻塞门
```

任何新机制必须有"完全失败时怎么办"的明确路径（见 §6 Fallback）。

每个 agent role 检查：

#### 输出格式

**第一部分：状态表**

|---|---|---|---|---|---|

**第二部分：红线问题清单**

每条标注 role / 问题 / 严重度 / 建议。

**第三部分：隐性假设清单**

列出 pipeline 对每个 agent 的隐性假设（如"historian 一定会用类比"、"economist 一定会输出 scenarios"、"fund_mgr 一定会接受 risk_gate finding"）。

每条标注：
- 假设是否被 prompt 显式要求？
- 假设是否被 schema 强制？
- 假设破坏会导致什么后果？

#### 执行原则

- 实际打开 prompt / schema 文件看，不凭印象
- Cross-session 或换模型跑（防自我确认偏差，参考 [§2.11.7](../governance/workflow/08-retro-node-and-pr.md) provenance 排序）

### 6.8 Degraded Run 机制

触发条件（任一）：
- fallback report 比例 > 50%
- 总延迟 > 90s
- 某 phase 完全失败

处理：
1. 标记 `degraded_run = True`
2. 用已有数据产出最终报告
3. 报告开头明确告知用户数据不完整 + 建议
4. compliance_block 强化
5. 决策日志标记 degraded

### 6.9 跨 Phase 链式失败兜底

最坏情况下产出 `emergency_report`：
- headline: "Trading Debate 分析降级 - 系统多组件失败"
- 简要 query 描述 + 已 fallback 的 phase 列表
- execution_plan: None
- compliance_block: 标准 disclaimer + 强化失败提示
- 用户能看到一个"系统报告了什么"，而不是 500 错误
